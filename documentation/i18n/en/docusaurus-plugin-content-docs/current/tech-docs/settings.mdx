## Working with Resources

Kubernetes resources form the foundation of any **Kube-native interface**.
For the UI to render data dynamically, the approach to describing resources, context, and scope must be standardized.

<h3>Scopes</h3>
Scope defines the interface context in which user actions are performed.

:::info Explanation

- **STOCK** is the primary interface area where the main work happens.
  It is divided into two subtypes:

  - **cluster**: when no `Namespace` is selected or when the switcher is set to _All Namespaces_. In this case, for example, the resource view should include an extra `Namespace` column.
  - **namespace**: when a specific `Namespace` is selected. In that case, the `Namespace` column becomes redundant and is hidden.

- **INSIDE** is an additional interface area usually intended for administrative tasks.
  Administrators can describe it using the same principles as STOCK while adapting it to their own needs.
  :::

<h3>Page Types</h3>

Kubernetes provides two different mechanisms for accessing resources: **builtin** and **api**.

- **builtin** are the basic resources available under `/api/v1`.
  These include standard Kubernetes entities such as `Pods`, `Secrets`, and `Services`.

- **api** includes all resources available through URIs of the following form:
  - `/apis/{apiGroup}/{apiVersion}/{kind}`
  - `/apis/{apiGroup}/{apiVersion}/namespaces/{namespace}/{kind}`

## Sidebar

<p>
  The Sidebar in in‑Cloud is a core navigation element. It provides access to interface resources and pages and is
  configured through YAML. This approach makes it possible to manage sidebar structure and content declaratively,
  without hard-coding it.
</p>

<p>
  Unlike static solutions, the in‑Cloud sidebar can be adapted to specific teams and their workflows. This makes it
  possible to configure different scopes such as user, administrative, cluster, or namespace and support different
  working scenarios without duplicating the interface.
</p>

## Breadcrumb

<p>
  Breadcrumb in in‑Cloud is an additional navigation element. It shows the path from the root level to the current
  page and helps users understand the context they are working in. Its main goal is to provide quick access to
  previous levels without returning to the sidebar or repeating a search.
</p>

<p>
  The trail is built declaratively from a YAML description. Each item has a key, display name, and link, and those
  links can use placeholders such as <code>\{cluster}</code>, <code>\{namespace}</code>, <code>\{apiGroup}</code>,
  <code>\{apiVersion}</code>, and <code>\{plural}</code>. This makes it possible to configure navigation flexibly for
  a specific workflow.
</p>

<p>
  Unlike the Sidebar, Breadcrumb does not define interface logic; it complements it. It is meant for convenience and
  time savings when moving across nested interface levels or quickly switching between clusters and namespaces.
</p>

## Navigation

<p>
  <strong>Navigation</strong> is the mechanism for configuring transitions between contexts in the in‑Cloud UI. It
  defines where the user should be redirected when selecting a project, instance, or namespace.
</p>

<p>
  Navigation works declaratively: when the value in a dropdown changes, the user is redirected to a predefined route.
  Two templates are defined for each context type:
</p>

<ul>
  <li>
    <code>clear</code>: the route used when the value is reset, for example "all projects"
  </li>
  <li>
    <code>change</code>: the route used when a new value is selected
  </li>
</ul>

<p>The following placeholders are supported in routes:</p>

    </tr>
    <tr>
      <td>
        <code>\{value}</code>
      </td>
      <td>Newly selected value (project, instance, or namespace)</td>
    </tr>
  </tbody>
</table>

## Factory

<p>
  The <code>Factory</code> resource is used in the in‑Cloud UI to build interfaces declaratively from YAML
  descriptions. It acts as a description of a page or part of a page and includes:
</p>

<ul>
  <li>data retrieval through the API</li>
  <li>visual composition from components</li>
  <li>nesting and grouping components into a structure</li>
  <li>work with JSONPath expressions and URL variables</li>
</ul>

<h3>URL Variables</h3>

<p>
  All paths in <code>urlsToFetch</code> and other fields can contain variables in curly braces that are substituted
  during rendering:
</p>

<CodeBlock language="yaml" title="Placeholder example">
  {dedent`
    urlsToFetch:
      - cluster: "{2}"
        apiGroup: "apps"
        apiVersion: "v1"
        namespace: "{3}"
        plural: "deployments"
        fieldSelector: "metadata.name={6}"
  `}
</CodeBlock>

<h3>Data Processing</h3>

<p>
  Data fetched through <code>urlsToFetch</code> is available in all components through JSONPath syntax, including
  nested access:
</p>

<CodeBlock language="yaml">
  {dedent`
    text: '{reqsJsonPath[0][".items.0.metadata.name"]["-"]}'
  `}
</CodeBlock>

<CodeBlock language="yaml">
  {dedent`
    text: |
        {reqsJsonPath[0]['.additionalReqsData.0.items[?(@.metadata.name=="{reqsJsonPath[0][".metadata.name"]["-"]}")].containers.0.usage.cpu']['-']}-CUSTOM!!!
  `}
</CodeBlock>

<ul>
  <li>
    <code>reqsJsonPath[0]</code>: the first element from <code>urlsToFetch</code>
  </li>
  <li>
    <code>[".items.0.metadata.name"]</code>: the path to the required field
  </li>
  <li>
    <code>["-"]</code>: the fallback value if the target value is undefined
  </li>
</ul>

:::info
Please note a few important details:

1. `urlsToFetch` is an array in which each element contains query results filtered with the specified `labelSelector` and `fieldSelector`.
2. If the target API supports `watch` and is available through a socket connection, data is streamed in real time. Otherwise, a regular REST request is used.
   :::

<h3>Per-Request Error Isolation (reqIndex)</h3>

<p>
  When <code>urlsToFetch</code> contains multiple requests, a failure of one request <strong>does not</strong> cause
  all components on the page to crash. Each component can specify which request it depends on through the
  <code>reqIndex</code> parameter:
</p>

<CodeBlock language="yaml" title="Example: two requests, components bound to req0">
  {dedent`
    urlsToFetch:
      - cluster: "{2}"       # req0 — main resource
        apiVersion: "v1"
        plural: "nodes"
        fieldSelector: "metadata.name={7}"
      - apiGroup: "metrics.k8s.io"  # req1 — metrics (may be unavailable)
        apiVersion: "v1beta1"
        cluster: "{2}"
        plural: "pods"
    data:
      - type: parsedText
        data:
          reqIndex: "0"       # depends only on req0
          text: "{reqsJsonPath[0]['.items.0.metadata.name']['-']}"
  `}
</CodeBlock>

<ul>
  <li>
    When <code>reqIndex</code> is specified, the component checks errors <strong>only</strong> for that specific request.
    Errors from other requests are ignored, and the component renders its data normally.
  </li>
  <li>
    When <code>reqIndex</code> is <strong>not specified</strong>, the component behaves as before:
    if any request fails, the component shows an error (backward compatible).
  </li>
  <li>
    The <code>reqIndex</code> value is a string (<code>"0"</code>, <code>"1"</code>, ...) corresponding to the index in the <code>urlsToFetch</code> array.
  </li>
</ul>

   <h3>Typical Use Cases</h3>

<ul>
  <li>Resource detail pages such as `Pods`, `Deployments`, and `Nodes`</li>
  <li>Tables with YAML/JSON editing</li>
  <li>
    Dynamic tabs with tables (<code>EnrichedTable</code>)
  </li>
  <li>Log and terminal visualization</li>
</ul>

<h3>General Description</h3>

The resource belongs to the <code>front.in‑Cloud.io/v1alpha1</code> API group and has the following basic shape:

<CodeBlock language="yaml" title="Factory.yaml">
  {dedent`
    ---
    apiVersion: front.in‑Cloud.io/v1alpha1
    kind: Factory
    metadata:
      name: example-details
    spec:
      key: example-details
      urlsToFetch:
        - cluster: "{2}"
          apiGroup: "apps"
          apiVersion: "v1"
          namespace: "{3}"
          plural: "deployments"
      data:
        - type: antdText
          data:
            id: text-header
            text: Example title
  `}
</CodeBlock>

## CustomFormsOverride

The `CustomFormsOverride` component is used to customize dynamic resource editing forms in the in‑Cloud interface. It works on top of OpenAPI specifications and allows the behavior and structure of UI forms to be overridden declaratively.

<h3>1. Why CustomFormsOverride Exists</h3>

:::info
`CustomFormsOverride` exists to make the standard OpenAPI-based form more convenient, compact, and safe.
:::

It solves the following tasks:

- hides unnecessary or sensitive fields such as `metadata` and `status`;
- allows field types and behavior to be overridden;
- adds support for dictionaries and field dependencies;
- changes the rendering without rebuilding the UI.

## CFOMapping

The <code>CFOMapping</code> resource is used together with <code>CustomFormsOverride</code> to force an override of
<code>customizationId</code> during form preparation.

The form provider applies the following resolution logic:

1. If a <code>CustomFormsOverride</code> exists with the original <code>customizationId</code>, it is used.
2. Otherwise, the UI looks for a mapping in <code>spec.mappings[customizationId]</code> and checks that the target
   <code>customizationId</code> actually exists in <code>CustomFormsOverride</code>.
3. If neither the original nor the mapped ID is found, <code>fallbackId</code> is used.

:::info
`CFOMapping` is read as a single named resource selected by <code>metadata.name</code>, while the mappings themselves
are stored in <code>spec.mappings</code> as <code>source key -&gt; target customizationId</code>.
:::

<h3>Resource Example</h3>

<CodeBlock language="yaml">
  {dedent`
    ---
    apiVersion: front.in‑Cloud.io/v1alpha1
    kind: CFOMapping
    metadata:
      name: default-cfo-mapping
    spec:
      mappings:
        stock-namespace-apps/v1/deployments: stock-namespace-apps/v1/deployments-v2
        stock-namespace-/v1/services: stock-namespace-/v1/services-override
  `}
</CodeBlock>

<h3>Resource Fields</h3>

<table>
  <thead>
    <tr>
      <th>Field</th>
      <th>Type</th>
      <th>Purpose</th>
    </tr>
  </thead>
  <tbody>
    <tr>
      <td>
        <code>metadata.name</code>
      </td>
      <td>
        <code>string</code>
      </td>
      <td>Name of the mapping resource. Used by the UI for selection via `fieldSelector`.</td>
    </tr>
    <tr>
      <td>
        <code>spec.mappings</code>
      </td>
      <td>
        <code>Record&lt;string, string&gt;</code>
      </td>
      <td>
        Mapping dictionary from the source <code>customizationId</code> to the target <code>customizationId</code>.
      </td>
    </tr>
    <tr>
      <td>
        <code>spec.mappings.&lt;customizationId&gt;</code>
      </td>
      <td>
        <code>string</code>
      </td>
      <td>
        Target <code>customizationId</code> that the form will switch to if it exists in
        <code>CustomFormsOverride</code>.
      </td>
    </tr>
  </tbody>
</table>

:::tip
If the mapped <code>customizationId</code> is missing from <code>CustomFormsOverride</code>, the UI will not apply the
mapping and will fall back to <code>fallbackId</code> if one is specified.
:::

## CustomFormsPrefill

The <code>CustomFormsPrefill</code> resource lets you prefill values in custom in‑Cloud UI forms.
This simplifies data entry and ensures consistency when creating Kubernetes resources.

<h3>Resource Example</h3>

<CodeBlock language="yaml">
  {dedent`
    ---
    apiVersion: front.in‑Cloud.io/v1alpha1
    kind: CustomFormsPrefill
    metadata:
      name: v1.service
    spec:
      customizationId: stock-namespace-/v1/services
      values:
        - path:
            - metadata
          value:
            name: example-service
            namespace: default
        - path:
            - spec
          value:
            type: ClusterIP
            selector:
              app: my-app
            ports:
              - name: http
                protocol: TCP
                port: 80
                targetPort: 8080
  `}
</CodeBlock>

<h3>Resource Example (Object Format)</h3>

<CodeBlock language="yaml">
  {dedent`
    ---
    apiVersion: front.in‑Cloud.io/v1alpha1
    kind: CustomFormsPrefill
    metadata:
      name: v1.service
    spec:
      customizationId: stock-namespace-/v1/services
      values:
        metadata:
          name: example-service
          namespace: default
        spec:
          hosts:
            "*":
              kind: bar
  `}
</CodeBlock>

:::info
Both formats are supported. On the BFF side, the object format is normalized into the canonical

<code>spec.values[]</code> form, an array of <code>{`{ path, value }`}</code>, which is used by all consumers.

Normalization example:

<ul>
  <li>
    <code>metadata.name</code> → <code>{`{ path: ["metadata","name"], value: "example-service" }`}</code>
  </li>
  <li>
    <code>spec.hosts.*.kind</code> → <code>{`{ path: ["spec","hosts","*","kind"], value: "bar" }`}</code>
  </li>
</ul>
:::

## Plugins

There are two supported plugin types:

- Plugins with fixed names such as `plugin-header`, `plugin-navigation`, and `plugin-sidebar`, responsible for the corresponding UI blocks.
- Plugins with dynamic names, available at `:prefix/:cluster/:namespace?/:syntheticProject?/plugins/:pluginName/*`

Repository with a [plugin example](https://github.com/PRO-Robotech/openapi-ui-plugin-example)

Plugins must be configured in the chart so that `remoteEntry.js` is accessible to the user in the browser.
